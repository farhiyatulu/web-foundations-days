The most difficult part of this course for me was the Day 7 assignments. Estimating scale and designing the architecture were tricky because I had to turn numbers like 500,000 page views a day into about 5 per second, and then decide which component solves which problem. At first I added components just because they appear in diagrams. I overcame this by asking "what problem does this solve?" every time I added something, as in the URL shortener example, and by working through TicketHub step by step. The estimates showed that the big sale is about 660 times busier than a normal day, which explained why it needs a CDN, a cache and a waiting room. Double-booking also became clear once I understood that the database must be the only judge, using an atomic conditional update backed by a unique constraint.

For my QuickNotes capstone, I would improve how I explain scaling and trade-offs. Day 7 showed me that my reasoning is strongest when I start from the numbers, so I would add clear estimates and state one trade-off, such as accepting slightly stale cached data in exchange for speed. I would also show the request in the browser's Network tab during the demo, so the audience can see the API working and not only the finished page.

Next, I want to learn Node.js and Express so that I can turn my API designs, like the TicketHub endpoints, into a working backend. My first step will be following the Express introduction on MDN and building a small notes API.
